# AnyModel — туннель VLESS + REALITY

Для AnyModel я развернул туннель на Xray-core 26.11.9 с VLESS, XTLS Vision и REALITY поверх RAW/TCP. Для сравнения прямых запросов с запросами через туннель я собрал отдельный HTTP(S)-сервис и стенд на Node.js 26.13.1 LTS со строгим TypeScript.

[Отчёт с результатами замеров (PDF)](report/REPORT.pdf)

## Запуск на Ubuntu 24.04 LTS

Нужен отдельный VPS на amd64 или arm64 с входящим TCP через публичный IPv4. На VPS с собственным IPv4 разрешите входящий TCP/443. На VPS за NAT используйте назначенный провайдером порт, который пробрасывается на тот же порт VPS, и задайте его в `VPS_PORT` перед запуском bootstrap. Ограничьте SSH административным адресом. Для стенда используйте отдельный порт и открывайте его только на время согласованной проверки.

Из корня клона выполните команды. В `VPS_ADDRESS` укажите публичный IPv4 или DNS-имя VPS. В `REALITY_SNI` укажите проверенное назначение REALITY с валидным сертификатом, TLS 1.3 и ALPN `h2`. Имя назначения должно отличаться от адреса VPS.

```bash
sudo -H ./scripts/bootstrap.sh --port "${VPS_PORT:-443}" "$VPS_ADDRESS" "$REALITY_SNI"
sudo -H ./scripts/profile.sh issue reviewer
```

Bootstrap готовит Docker Engine и Compose и проверяет новую конфигурацию перед применением. Повтор с теми же параметрами сохраняет ключи и клиентские UUID. При ошибке запуска скрипт возвращает предыдущую конфигурацию. Выпускайте отдельный UUID на каждого проверяющего и на нагрузочный стенд.

Профили, ключи и конфигурация лежат во внешнем закрытом каталоге `~/.anymodel-tunnel` пользователя запуска. Для команд через `sudo -H` это `/root/.anymodel-tunnel`. Можно задать абсолютный `ANYMODEL_STATE` и использовать его во всех операциях для этого сервера. Команда `issue` выводит путь к файлу, который передаётся проверяющему приватно.

```bash
sudo -H ./scripts/profile.sh show reviewer
sudo -H ./scripts/profile.sh revoke reviewer
```

Отзыв пересоздаёт контейнер с обновлённым списком клиентов и закрывает активные соединения. После проверки отзовите временные профили и закройте порт стенда. Для завершения срока доступа отзовите профиль проверяющего и остановите сервер. Дату отсчитывают от фактической отправки комплекта.

Проверить обычный TLS через тот же порт с внешней машины можно с помощью OpenSSL.

```bash
openssl s_client -connect "$VPS_ADDRESS:${VPS_PORT:-443}" -servername "$REALITY_SNI" -tls1_3 \
  -alpn h2 -verify_hostname "$REALITY_SNI" -verify_return_error </dev/null
```

Для быстрой проверки импортируйте приватный профиль VLESS в Happ и подключитесь. Затем откройте [страницу проверки выходного IP](https://api.ipify.org) и сверьте показанный адрес с публичным IP VPS. Адрес и порт из профиля предназначены для подключения клиента Xray. После повторного запуска bootstrap снова проверьте загрузку с тем же профилем.

## Стенд измерений

Установите Node.js по `.nvmrc` и curl с форматом `%{json}`. На VPS для метрик нужны `ss` из iproute2 и `nsenter` из util-linux. Сохраните сертификаты, профили и рабочие измерения вне дерева репозитория.

```bash
nvm use
npm --prefix bench ci
npm --prefix bench run check
```

На машине с контролируемым назначением запустите сервис. Укажите адрес прямого клиента и адрес, с которого TCP-соединение от Xray видит сервис. Для HTTPS передайте `--cert` и `--key`. Если используется свой удостоверяющий центр, передайте его сертификат клиенту через `--cacert`. Сервис на том же VPS допустим, если обе ветки достигают его публичного адреса. В таком стенде путь от прокси до назначения проходит внутри или рядом с VPS, что влияет на сравнение.

```bash
node bench/cli.ts origin --bind 0.0.0.0 --port "${ORIGIN_PORT:-18443}" \
  --allow "$CLIENT_IP" --allow "$EGRESS_PEER"
```

На тестовом VPS за NAT повторите проверку `/peer` с внешнего клиента и через Xray. Если провайдер не маршрутизирует запрос к собственному публичному IPv4 обратно на VPS, для стенда на одной машине направьте только запросы с Docker-моста на порт origin. Для этого варианта передайте публичный IPv4 в `VPS_ADDRESS`, а назначенный тестовому сервису порт в `ORIGIN_PORT`.

```bash
network_id=$(sudo docker network inspect anymodel-tunnel_default --format '{{.Id}}')
bridge=$(printf 'br-%.12s' "$network_id")
gateway=$(sudo docker network inspect anymodel-tunnel_default --format '{{(index .IPAM.Config 0).Gateway}}')
origin_rule=(-i "$bridge" -d "$VPS_ADDRESS/32" -p tcp --dport "$ORIGIN_PORT"
  -m comment --comment anymodel-controlled-origin -j DNAT --to-destination "$gateway:$ORIGIN_PORT")
sudo iptables -t nat -C PREROUTING "${origin_rule[@]}" 2>/dev/null ||
  sudo iptables -t nat -I PREROUTING 1 "${origin_rule[@]}"
```

В этом случае в `EGRESS_PEER` укажите IPv4 контейнера Xray, подтверждённый запросом к `/peer`. После проверки удалите правило командой `sudo iptables -t nat -D PREROUTING "${origin_rule[@]}"` и остановите тестовый сервис.

На измерительном клиенте подготовьте конфигурацию Xray из выделенного профиля и запустите закреплённую версию Xray с SOCKS на 127.0.0.1:1080. Если клиент работает в контейнере, укажите `--listen 0.0.0.0` и публикуйте SOCKS только на loopback хоста. Файл конфига создаётся с правами 0600.

```bash
node bench/cli.ts client --profile "$PRIVATE_PROFILE" --output "$CLIENT_CONFIG"
xray run -config "$CLIENT_CONFIG"
```

В другом терминале на VPS запустите сбор метрик. `IFACE` задаёт внешний сетевой интерфейс. После завершения прогона остановите сбор с помощью Ctrl+C. На Mac можно проверить поток Compose с параметрами `--container-only --samples 3`.

```bash
sudo -H "$(command -v node)" bench/cli.ts metrics --iface "$IFACE" --output "$METRICS_JSONL"
```

На измерительном клиенте запустите парные прогоны. `ORIGIN_URL` — базовый URL одного и того же сервиса для обоих режимов. Добавьте `--probe-only` для проверки размера и длительности без нагрузочных окон. После прогона скопируйте файл серверных метрик на машину с результатами.

```bash
node bench/cli.ts run --origin "$ORIGIN_URL" --proxy-peer "$EGRESS_PEER" --output "$RUN_JSONL"
node bench/cli.ts results --input "$RUN_JSONL" --metrics "$METRICS_JSONL" > "$SUMMARY_CSV"
```

Перед нагрузкой я сверяю адрес источника запроса, манифест и SHA-256 файла. В каждом окне я запускаю длинные передачи и отдельный поток коротких запросов. На каждый запрос приходится одно TCP-соединение. Мультиплексирование отключено. Уровни 1, 4, 8, 16 и 32 означают число длинных передач. До 64 можно расширить флагом `--max-streams 64`. Интервал по умолчанию 25 секунд, три повтора. Пропускная способность учитывает только полные успешные ответы. CPU Xray дан в процентах одного vCPU и в процентах всей ёмкости VPS.

Для оценки стабильности я использую три повтора, минимум 100 коротких запросов в базовом режиме и под нагрузкой, а также минимум 30 длинных передач на уровень. Допустимые пороги составляют 1% ошибок и 2× базового p95 полного короткого запроса. Пиковое число TCP-соединений я сверяю с серверным счётчиком.

## Контроль через Happ

После внешнего прогона выдайте отдельный профиль через `profile.sh issue rf-probe`. На стороне сервиса передайте `--check-secret-file` с результатом `openssl rand -hex 16`, `--expected-vps-peer` с подтверждённым выходным адресом и `--audit-file` с новым путём вне репозитория. Приватные ссылки имеют вид `/check/TOKEN/direct` и `/check/TOKEN/tunnel`. Они возвращают один и тот же файл 256 КиБ.

В журнале сравните UTC, метку ссылки и наблюдаемый маршрут. Запись `observedRoute: "vps"` формируется по фактическому адресу TCP-соединения. Имя ссылки само по себе ничего не подтверждает. Сопоставьте запись с завершённой загрузкой на телефоне, фактическим типом сети и названием оператора. При наличии домашнего Wi-Fi и мобильной сети выполните два отдельных прогона. По завершении остановите временный сервис и отзовите выданный для этого прогона профиль. Ссылки для скачивания действуют, пока запущен временный сервис.
